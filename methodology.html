我怎么做 0-1 产品

我做 AI 产品，不是先憋一份 PRD 再找人写代码，而是先抓一个真实需求，用最小原型证明它值钱，再把它做成真能跑的系统。这页记的是我一遍遍试出来的干法——2026.08 拿商业空间那个案例复盘过，更新了一版。

0-1 验证先原型再放大第一性原理质疑数字诚实安全与治理前置

1. 我理解的 0-1 AI 产品

不少项目把 AI 当成一个新功能、或者一道技术题来啃，最后交一份方案或一个 demo。我的体会是：AI 真要省钱省事，得钻进用户每天实际在干的那件事里，替他把某个环节真的干掉，而不是多给他一个玩具。

所以我的交付物优先是能跑的系统或流程：能转写的流水线、能出报告的调研模板、能一键投屏的家庭 kiosk、能复用的测评 Skill。方案文档只是副产品。

两条底层判断：① AI 不重要，业务才重要——给企业服务，六成精力花在业务梳理上，老板买的是结果，不是工具或过程；② 最难的一公里不是"学会用"，是"用上了"——聪明人很多，动手把 AI 接进真实流程的人少。

2. 我的交付节奏：先跑通，再沉淀，再复用

我不会一上来就做大而全的规划。习惯先把一个真实需求拆到最小闭环，跑通后再扩展。

阶段动作产出
第 1 周选一个真实需求，用 AI 工具搭一个可运行的最小原型验证报告：原耗时 vs AI 耗时、字段可用率、人工修正项
第 2 周把验证过的步骤封装成可复用模板 / Skill可复用模板 + 权限边界清单 + 版本记录
第 3–4 周在第二个场景复用，验证跨场景稳定性修正率是否下降、交付速度是否提升
我的判断标准很简单：同样的活，下次能不能更快、更稳、更少人工返工。能，就说明这个 Skill 成立了；不能，就回到验证阶段找原因。

我看待节奏是这样的：先用 48 小时做出个最小闭环、验证方向对不对；再用 48 天把它做成真能跑的硬货；最后用 48 周磨成团队级别的能力。核心就是别一上来就画大饼——先把能验证的东西交出来。项目里每一次"先跑通再扩展"，都是这个节奏的实操。

我每交一段活，都会让它滚成一个循环：干活时留下过程记录，事后沉淀成笔记和上下文，再提炼成方法论、固化成能复用的 Skill，最后让自动化替掉那些重复劳动。一个项目走完，下一轮起点就高了。

3. 我的现场工作法

我把现场能力拆成四件事——听出真问题、把服务谈下来、稳定交付、教会对方用上。它们与 AI 本身无关，但决定了 AI 能不能落地：

能力我的做法
顾问：听出真问题能跟业务方聊得起来，一针见血看出病症、给出药方；不拿现成模板硬套，先和用户把真实约束列清楚：数据能不能出境、有没有合规要求、关键决策人是谁、失败成本有多高。
销售：把服务谈下来懂业务和项目怎么干，能用算账公式谈价——"省了多少钱 ÷ 收多少钱"用数字说服，而不是卖功能。
工程：稳定交付架构设计 + 稳定交付；后段难缠的 bug，多半是前段架构设计的问题，所以架构阶段就把坑堵住。
教学：教会用上不是讲课，是带练——带客户的人跑一遍、定制工具、让关键流程离开我也能转。
小步验证：复杂任务先拆成 2 小时能跑完的最小闭环，确认有价值再继续投入，而不是憋大招。关键交付节点必须有人工确认；AI 输出异常要能回滚；敏感数据泄露有响应路径。

从场景切开做产品，而不是从功能开始。不做"大市场"产品，先锁一个具体人群的具体场景。比如给"会一点英语、但开会不敢开口"的职场人做的 7 天反应训练——不做"英语学习"这种大命题，场景精确到开会汇报被主管追问。判断标准一句话：为谁、在什么场景、解决什么，能一句话说清才动手。然后把虚的需求拆成用户每天能感知到的进步（反应时间、完成度这类可量化指标），再连成一条价值闭环：用户进入 → 获得价值 → 愿意传播。功能是这条链上的零件，不是目标。

4. 我的安全与治理习惯

数据安全对我来说不是"安全不安全"的判断题，而是怎么运的选型题。我通常给客户一张四档部署菜单，明码标价，让客户基于业务价值和风险承担能力做选择——而不是把安全变成项目开工前的一堵墙：

档位部署方式取舍
第一档公有云 + 第三方模型（关闭训练、控制日志）启动最快、成本最低，适合公开/低敏感数据
第二档境内云环境（账号、加密、访问控制）数据不出境但可上云，迭代仍快
第三档企业 VPC / 专有云（私有网关调模型）数据不离开企业控制域，成本与运维上升
第四档完全本地化 / 物理隔离（推理+向量库+日志全本地）成本最高、交付最慢，适合医疗/军工/金融核心

安全是要花钱买的东西，不是天然正确的选项。要是业务收益盖不住安全方案的成本，就换个场景做，别把整个项目无限期卡着。选型定下来就写进工作说明书，免得后面扯皮。

项目我的默认做法
数据存储用户资料优先用境内云，不默认落境外服务。
模型算力默认境内模型；如允许用海外模型，切换前明确告知。
日志训练所有模型 API 调用关闭"用于训练"开关。
敏感数据财务数据、合同条款等敏感内容在本地环境处理，不进云端模型。
对外展示真实客户文件进作品集 / 知识库前先脱敏：泛化主体与地址、屏蔽联系人，只保留通用参数——案例能安全展示，才谈得上复用。
权限Agent 只能读任务相关数据，不能访问其他项目资料。

5. 我用来约束自己的五层清单

层落地动作
Context 边界明确哪些资料可进外部模型、哪些必须留本地 / 专属环境；企业的知识、经验、文档，不能因为"要训练 AI"就默认全部开放。
Skills 沉淀把反复出现的交付步骤封装为模板，保留版本记录与变更记录——一旦封装成 Skill，它就从个人方法变成可被反复执行的规则，必须明确谁有权管理。
Agent 权限细化到具体行动：能读哪些文档、调哪些系统、发哪些消息、多少钱以下自动执行；关键动作必须人工批准。
责任边界AI 辅助决策，但我对交付负最终责任——AI 可以承担工作，但不能成为责任消失的借口。
异常升级关键交付前必须人工确认；异常输出必须回滚；敏感数据泄露立即响应；治理嵌入每一次真实行动，不是年度审查时挂墙上的声明。

6. 每次交付后我会问自己的三组问题

维度自检问题
能力积累上次交付的 Context 和修正，有没有沉淀成 Skill？同样的活下次能不能更快？
治理Agent 权限边界写清楚了吗？关键交付节点有我的人工确认吗？
用户价值这个交付有没有让用户某个真实环节变快、变准、变便宜？有没有减少不必要的协调？
数字诚实"3 天 → 3 小时 ≈8×"这类数字，我标注了是估算还是实测吗？没有对照实验数据，就明确说"待验证"，不把叙事当实证。

7. 最近一次复盘：商业空间案例给我的三条硬原则（2026.08）

原则含义案例验证
先质疑惯例，再谈方案行业惯例不是理由：先找"这条规矩是谁定的、它护的是什么"，再决定守不守。只有物理级约束不可打破，其余都可质疑。「AI 须让客户看见」是惯例 → 直接扔掉，改成"隐形产能、不碰甲方认知"——甲方"AI 不如设计师"是硬约束，教育成本高于价值。
数字诚实：估算与实测分开讲"提速 8×""吞吐翻倍"这类数字，必须说清是估算还是实测，无对照实验数据就标"估算"。商业空间"竞标 3 天→3 小时 ≈8×""接单吞吐 40%→90%"都是战略估算，对外只讲"可行性验证已跑通"，不吹实证。
流程红线：交付链不可抢跑关键交付链的产物有明确前置依赖，跳级 = 返工。硬装交付链 = 概念 → 方案效果图 → 施工图 → 材料清单；材料清单是施工图阶段成果，前置是效果图定稿，不得提前。
这三条是从 商业空间设计 AI 交付链 的真实任务书端到端验证里长出来的——第一性原理筛子（知识密度 / 重复劳动 / 中间层冗余 / 反馈慢 / 数据孤岛）也是这套判断的日常工具。
