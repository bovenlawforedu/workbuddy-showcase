SSS 投屏启蒙系统

一个具体的家庭刚需（给老人一键投屏放儿歌、严格每天 5 集、防误触），被我拆成一套完整的 App 需求和架构，能看出"先对齐需求、再搭方案骨架、排好科学课程体系、最后上可扩展规则引擎"这套产品判断。

真实家庭需求kiosk 防误触端到端

1. 背景与需求

真实场景：1.5 岁幼儿的英语启蒙，每天严格看 5 集 SSS；日常操作者是不熟悉科技的老人，家里有小米电视，没有 Mac。痛点：把「选集 → 投屏 → 控量」这件对老人太复杂的事，压成一个按钮。

10 条核心需求（已与用户逐条对齐）：端到端投屏、纯手机 App、一键投屏 + 一键播放、资源本地化 + 科学标签、分龄 + 主题双维分类、每天 5 集周期规划、播满 5 集自动停、素材可自助添加、规则可调、kiosk 防误触。

2. 我做了什么

① 方案骨架

执行端 = 手机 App，视频存本地，直投同 WiFi 电视；离线可用。iOS 走系统 AirPlay，Android 走 DLNA（手机起本地 HTTP 服务供电视拉流），预留 HarmonyOS 扩展。技术栈：Flutter 共享 UI 与排期/规则逻辑 + 平台通道调原生投屏。

② 两层分类与课程体系

维度1 年龄阶段（入门期→认知扩展→语言结构→叙事文化）；维度2 启蒙主题（打招呼/身体/动作/情绪/routine/颜色/数字/动物/食物/字母拼读/天气星期/童谣/节日）。排序原则：先具象高频、后抽象低频；先听说、后结构。每 5 集 = 一个周期块。

③ 可扩展规则引擎（不写死）

参数化 episodes_per_day(5) / block_days(14) / counting_mode / stop_rule / block_order，支持阶段级覆盖。规则变更只对「变更日之后」生效，历史打卡原样保留——关键的产品伦理决策。

3. 交付与结果

交付物：完整 App 需求与架构（Flutter + 原生投屏通道 + 本地 SQLite + 规则引擎 + kiosk 防误触），含两层科学分类体系与「已确认决策清单」。

结果：把"选集→投屏→控量"这件对老人太复杂的事，压成一个按钮——背后是 AirPlay/DLNA 的差异，老人只看到一个动作。kiosk 防误触是非技术用户可用性的硬指标；规则引擎「变更只影响日后、历史保留」是对用户历史的尊重，也是蹲在现场才看得见的约束。好需求不是列功能，是先钉死约束：操作者是谁、设备是什么、红线是什么——约束清楚了，方案反而简单。

与 FDE 岗位的对应

FDE 能力本项目证据
进现场摸需求（Echo）进家庭真实场景（老人+幼儿+小米电视），把需求逐条钉死
Forward Deploy（端到端落地）把投屏/防误触/控量部署成可跑的 App 架构，而非想法
一线诊断kiosk 防误触、规则变更只影响日后——蹲在现场才看得见的约束

技术栈：Flutter + 原生投屏通道（iOS AirPlay / Android DLNA）+ 本地 SQLite + 本地视频目录。分发：iOS TestFlight、Android APK 侧载（个人工具）。
