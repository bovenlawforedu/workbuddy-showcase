谈话录音 AI 归档流水线

把「线下谈话录音散落、无法检索」这个真实痛点，做成一条本地优先、隐私优先的 AI 流水线——音频入 → 双引擎转写 → 本地 LLM 结构化纪要 → 归档 → 同步。这是 FDE「把系统真正端到端搭起来跑通」的硬样本。

进现场摸需求Forward Deploy一线诊断隐私优先架构

1. 背景与痛点（进现场识别，而非拍脑袋）

线下谈话 / 通话录音散落在手机里，没有结构化归档和检索能力。现有录音转写服务都要上传到第三方服务器，不符合隐私需求；本地 Whisper 质量够用，但静音段有幻觉问题需要工程解决。

我的产品判断（进现场后做的，不是关起门来定）：

  • 隐私优先路线：录音不经过任何云端 App 直传 Mac 本地处理，凭证不落盘（运行时加载）。
  • 三节点解耦架构：采集 → 处理 → 归档，各节点职责单一、可独立替换。
  • 为什么不用现成方案：现成服务都要上传第三方，不符合隐私约束；本地方案的真实卡点在静音幻觉，是工程问题而非不可用。

3. 三个真问题（面试最值得讲）

① Whisper 静音段幻觉

录音开头 7 秒静音触发 Whisper 输出幻觉文本并提前终止解码，后面真实语音全部丢失。根因是 Whisper 长静音已知行为 → 写 smart_transcribe.py 用能量检测切出纯语音段逐段喂 Whisper，跳过静音；段间留 0.5s 重叠防边界丢词。

② 通义听悟 API 集成（无官方 SDK）

阿里云 OpenAPI 用 ROA 签名（HMAC-SHA1），还需自己上传 OSS、生成签名 URL、轮询任务状态 → 手写 tingwu_transcribe.py 全链路（OSS PutObject / 签名 URL / ROA 签名 / 创建任务 / 轮询 / 下载解析 / 清理）。

③ 本地小模型纪要质量不稳定

qwen2.5-1.5b 会复读、输出客套话、拆散中文标题 → 在 ai_pipeline.sh 写大量后处理正则，强制 8 板块标准结构，兜底回填原始转写。
